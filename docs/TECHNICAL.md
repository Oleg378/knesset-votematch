Проверка на GitHub `.github/workflows/pipeline.yml` при каждом пуше, задевшем `pipeline/`, `data/`, `manual/` или `export/`: восстанавливает снимок (ключ в секрете `SNAPSHOT_DEPLOY_KEY`), `make check`, `make data`, `pipeline/export_compare.py` — экспорт в git должен совпадать со сборкой по содержанию (поля `source_commit` и `generated` не сравниваются).

## 2. Данные

**Источники.** OData v4 Кнессета (созывы 24–25; старый `Votes.svc` закончился на 2021 годе); страницы ЦИК (списки и кандидаты 2026, читаются через браузер заказчика); `KNS_PersonToPosition` (должности министров и заместителей). Сторонние агрегаторы — только для сверки.

**Что используется.** Голосования по законопроектам на четырёх стадиях (предварительное, первое, второе по статьям, третье); поправки (הסתייגויות), роспуск Кнессета, тайные и поднятием рук — нет. Действия депутата: внесение (`is_initiator`), присоединение, отзыв подписи (не вычитается), «за», «против», «воздержался», «присутствовал» (последние два в позицию не входят).

**Очистка.** Дубли строк от сервера удаляются; даты читаются строками (DuckDB уводит `+03:00` в UTC); листание по ключу (`$skip` деградирует к 40-й странице); 2 потока (больше — HTTP 481); созыв — по дате; 11 голосов без фракции — ближайший интервал членства.

**Ограничения данных.**

| # | Ограничение | Последствие |
|---|---|---|
| L1 | Даты внесения частного законопроекта нет (`PublicationDate` пуста у 98 %) | фракция инициатора на момент внесения не определяется |
| L2 | В `KNS_Bill` только текущий статус | этап, где законопроект застрял, восстанавливается по датам |
| L3 | Решений Министерского комитета по законодательству нет | блокировка видна только по голосу коалиции «против» на предварительном чтении |
| L4 | Поимённых голосований в комиссиях нет | блокировка в комиссии видна лишь косвенно |
| L5 | `IsContinuationBill` пуст | перенесённые законопроекты — по этапу 9 и старому Id |
| L6 | В дни ротаций 121 депутат (9 голосований), у 4 строк не определён блок | пренебрежимо |
| L7 | Особое большинство (61) для основных законов не проверяется | исход отдельных статей может быть неточным |
| L8 | Голосования поднятием рук и тайные не поимённые | не используются |
| L9 | OData только из Израиля, страницы комиссии за Cloudflare | выгрузка с израильского IP, страницы — через браузер |
| L10 | У правительственного законопроекта нет инициатора и ведомства | входит в позицию только голосами (SU п. 31) |

## 3. Признаки голосований и лагерь

| Признак | Определение |
|---|---|
| `p_for` (фракция) | за / (за + против); воздержавшиеся и неголосовавшие не в знаменателе |
| `cohesion` (блок) | max(за, против) / (за + против); сплочённость ≥ 0,9 |
| `participation` | присутствовали / состав на дату; низкая явка < 25; бойкот: участие одного блока < 0,1 при другом ≥ 0,4 |
| `split_pattern` | `no_blocs`, `one_bloc_only` (< 3 голосующих), `consensus`, `cross_bloc_majority`, `bloc_line`, `bloc_line_with_dissent` — по порядку |
| `dissenting_factions` | фракции с ≥ 2 голосами против линии своего блока |

**Правительство** — фракция с министром или заместителем министра на дату (должности `[31, 39, 45, 50, 51, 57, 65, 73]` и `[40, 59, 285079]`); человек → фракция по членству на дату (если не депутат — ближайшее членство в созыве). Переходные окна от начала созыва до формирования правительства (2021-04-06 – 06-13, 2022-11-15 – 12-29) исключены.

**Лагерь** для очистки голосов и сигналов O/G — правительство по министрам **или** фракция без министров, голосующая с большинством правительства в ≥ 90 % из ≥ 200 голосов в созыве (так РААМ в 24-м). Лагерь законопроекта: правительственный — коалиции; частный — лагерь большинства инициаторов на дату голосования.

## 4. Метки

**Схема.** У законопроекта 1–2 главные и до 5 побочных тем, каждая со знаком «+»/«−» (увеличивает или уменьшает величину темы); побочные наравне с главными. Источник разметки — название и пояснительная записка; статьи бюджетных пакетов (חוק ההסדרים, 8 пакетов) — текст статьи, размечены агентом, а не Jev; голосование за пакет целиком несёт главные темы его статей. Технические законопроекты (например, о зимнем времени) исключены.

**Слои поверх разметки** (`pipeline/labels.py`, по порядку): стадии разделения тем 2…10 (`LATER`) → `overrides.json`: `labels` (точечные правки), `remove`, `flip`, `add` → `nested_removals.json` (вычитание общих законопроектов у вложенных пар). Правила изменения метки — SU п. 37; все проверенные пары «законопроект × тема» — `labels/label_check_coverage.csv` (инвариант I6).

**Темы.** Реестр — `data/directions/registry.csv`: у каждой темы, проходящей отбор, либо вопрос, либо решение (`duplicate`, `split`, `basket`, `technical`, `no_statement`, `dropped_dup`; `pending` — в процедуре). Определения тем — `data/directions/DIRECTIONS_LIST.csv` (один список 255 тем; `labels.directions()`) и `split/planN.json`.

**Метаданные утверждений** (`data/quiz/statement_meta.csv`): `interest` 1–5 (среднее четырёх слепых оценок: две исходные и две аудита 2026-10-25; шаг 0,25), `area` (13 кодов), `sim_group` (группа «один вопрос для избирателя»; пары, на которых сошлись две слепые группировки). Используются только порядком вопросов.

## 5. Позиция депутата по теме

P = A + 0,25·V + 0,25·O + 0,25·G; отсутствующая компонента — 0 (SU п. 34).

| Компонента | Что | Как |
|---|---|---|
| A | авторство | средний знак внесённых депутатом законопроектов по теме (все инициаторы равны; главные и побочные темы наравне); **не центрируется**: не вносил — 0 |
| V | голоса по частным законопроектам своего лагеря | знак темы × голос (+1/−1); остаток после регрессии на долю голосов депутата «на стороне правительства» внутри созыва × темы (среднее 0) |
| O | голоса по законопроектам чужого лагеря | знак темы × голос, без вычета оси, четыре стадии, вне переходных окон |
| G | голоса коалиции по собственным правительственным законопроектам | зеркало O, те же правила |

Голоса по бюджетным пакетам (целиком и по статьям) не входят ни в O, ни в G. Созывы объединяются (A — по всем законопроектам; V, O, G — среднее по созывам с весом по числу голосов). Веса 1 / 0,25 / 0,25 / 0,25 подобраны по устойчивости позиций между созывами и заморожены. Слой «отношение к правительству» (доля голосов с большинством правительства, по созывам) считается отдельно и пользователю не показывается.

## 6. Позиция списка и явность

Список 2026 → его кандидаты, бывшие депутаты 24–25 (`manual/candidate_mk_26.csv`, совпадения exact/manual; имена — `manual/mk_names_en.csv`; партия-участница — `manual/party_names_en.csv`). Позиция списка по теме — среднее P по бывшим депутатам с действием по теме, равные веса. Покрытие: без бывших депутатов — не оценивается; один — показывается, не ранжируется; < 3 в первой десятке — предупреждение. Явная позиция: |p| ≥ 0,2 (CLOSE), ≥ 2 депутата, ≥ 2 разных названия законопроектов; иначе «нет явной позиции».

## 7. Отбор тем в квиз

`pipeline/quiz_select.py`, пороги заморожены (SU п. 39): по оцениваемым спискам (status ok) с ≥ 3 депутатами по теме — не меньше 8 списков, разброс позиций (SD генеральной совокупности) ≥ 0,25, не меньше 5 разных названий законопроектов (повторное внесение — одно). Остатки разделённых тем и технические темы вопросов не получают. Ось правительства (|r| ≥ 0,8 с долей голосов с правительством) не ограничивает отбор; в ядре квиза таких тем не больше половины.

**Текущее состояние (2026-10-22).** Тем с позициями списков — 469; вопросов — 123 (ключи 82 «+», 41 «−»); решения в реестре — 315 тем (123 quiz, 110 split, 50 duplicate, 14 technical, 7 basket, 6 no_statement, 5 dropped_dup). Списков: 12 оцениваются, 4 с одним бывшим депутатом не ранжируются, 22 без истории. Исправления меток: снято 1 607, добавлено 632, сменён знак у 52; вложенных двойных учётов снято 26 522. Законопроектов в экспорте — 6 666.

## 9. Сопоставление ответов со списками (`quiz_match.py`)

- Ответ → число: полностью согласен +1, скорее +0,5, скорее нет −0,5, нет −1; «не уверен, пропустить» — утверждение показано, но не отвечено и не участвует (на сайте и в терминале одни и те же четыре ответа [У 2026-10-23]; в листах ответов и сессиях допустимы ещё 0 — нейтрально, считается ответом, и «не знаю» — пропуск); умножается на ключ утверждения.
- Близость = косинус между вектором ответов и вектором позиций списка по отвеченным утверждениям, где у списка есть позиция; вес утверждения 1/n на тему (сейчас всегда 1). Сжатия нет (K = 0).
- Покрытие = доля веса ответов, по которым у списка есть позиция; ранжируются списки с покрытием ≥ 0,5 и ≥ 2 бывшими депутатами; остальные — отдельно с пометкой.
- Размены (`tradeoffs`): для каждого списка топ-5 по порядку — утверждение, которое больше всего ему добавило, против утверждения, которое больше всего сняло; вопрос задаётся, только если удвоение веса одной из тем меняет порядок топ-5; выбранная тема ×2; не больше 5, по одному на список.
- Пояснения (`quiz_report.py`): по каждому утверждению — сторона списка («points toward / against / no clear position»), основание: законопроекты бывших депутатов в сторону ответа и против, число голосов по частным законопроектам, по законопроектам чужого лагеря и по правительственным своего лагеря; подпись, если сторону дали голоса, а не законопроекты.

## 10. Порядок вопросов (`quiz_flow.py`, параметры в `FLOW`)

**Ядро (8, одно для всех).** Оси — SVD матрицы «оцениваемые списки × утверждения» (нет позиции → 0, столбцы центрированы), первые 4 оси. Балл утверждения на оси k = нагрузка² × чистота (доля нагрузки на этой оси) × (интерес/5)². Слоты по осям 4/3/1; показ с чередованием осей. Фильтры: явные позиции на обеих сторонах; одно утверждение на тему; интерес ≥ 3; одна область; не два из одной группы похожести; не больше половины на оси правительства; |r| < 0,8 с уже выбранными.

**Уточняющие (7, по одному после ответа).** Ранжирование по текущим ответам (как на экране результатов). Кандидаты — не показанные утверждения, минус группа похожести показанных, минус (если остаётся выбор) область предыдущего вопроса и |r| ≥ 0,9 с показанными, минус (если остаётся выбор) утверждения без явных позиций на обеих сторонах среди 4 ближайших списков. Балл = Σ по претендентам (списки с отставанием от лидера < 0,1, иначе второй) |p_лидер − p_претендент| / (отставание + 0,05) × (интерес/5)². Максимум; при равенстве — меньший номер; до ранжирования — наибольший разброс по всем спискам.

**Длина:** 8 + 7 ответов + до 5 разменов. Пропуск («не уверен») не считается: утверждение заменяется следующим (сначала остаток основных, потом уточняющие), пока не набрано 15 ответов или не показано 30 утверждений (`max_questions`) — что раньше; счётчик на экране — номер даваемого ответа, после пропуска не двигается. «Ответить ещё» продолжает уточняющие до конца пула. Правило остановки по разрыву (`stop_gap`) есть, выключено.

## 11. Экспорт и контракт с фронтом

`export/quiz_core.json` (параметры порядка, ядро, его утверждения), `quiz_data.json` (параметры, утверждения с метаданными, темы, списки с позициями и составом), `quiz_bills.json` (законопроекты, депутаты, голоса), `quiz_data.schema.json` (одна схема на три файла, проверяется при экспорте), `golden.json` (34 эталонных случая: ответы → ранжирование, размены, пояснения, порядок вопросов). Что считать и показывать на фронте — `export/WEB_CONTRACT.md`. `quiz_data.json` несёт и `fetched` — день последнего скачивания таблиц законопроектов Кнессета (время записи `raw/bills/bill.json`); эту дату сайт показывает в конце страницы методологии («Data: …»), `generated` — день экспорта. `stats.json` — текущие числа экспорта (утверждения, списки по статусам, законопроекты, депутаты, темы, размеры файлов в КБ; пишет `export.py`, в сайт не входит). Тексты сайта — `export/quiz_texts.json`, правится вручную, `export.py` его не пишет: название, ответы, пометки, строки пояснений, подписи всех экранов, страница методологии (контракт — `WEB_CONTRACT.md` § 7). Шаблоны: `{имя}` и `{имя?один|много}`; числа — только подстановки (для методологии — из `quiz_data.json`, включая пороги отбора `params.SELECT_*`); допустимые имена каждого ключа перечислены в `web/src/texts.ts`, из его схемы порождается `export/quiz_texts.schema.json` (`cd web && npm run schema:texts`). Фронт встраивает файл в сборку (не загружает: он нужен стартовой странице раньше данных); эталон на Python отрисовывает из тех же шаблонов ответы и строки пояснений (`pipeline/texts.py`, `quiz_report.py`) и пометки (`quiz_match.py`), поэтому `golden.json` проверяет и тексты; после правки `answers`, `notes` или `explain` — `make data`. Порт на TypeScript (`web/src/engine/`) обязан воспроизводить эталоны с точностью 1e-9. Фронт не читает ничего, кроме `export/`.

**Инварианты (`make check`).** I1 каждое утверждение проходит отбор · I2 одна тема ↔ одно утверждение · I3 нет утверждений на остатках и технических темах · I4 у каждой проходящей темы есть утверждение или решение в реестре · I5 нет вложенных пар среди тем утверждений · I6 каждая метка на теме утверждения проверена · I7 экспорт соответствует текущим утверждениям · I8 `export/quiz_texts.json` проходит свою схему · I9 числа, набранные в документах (здесь — «Текущее состояние»: вопросов, списков, законопроектов в экспорте; в `export/WEB_CONTRACT.md` § 1 — размеры файлов), совпадают с `export/stats.json` (счётчики точно, размеры ±15 %) · I10 `export/golden.json` актуален (пересчёт эталонных случаев даёт те же ранжирование, пометки и строки пояснений).

## 12. Измеренные свойства метода

- Устойчивость позиций списков между созывами 24 и 25 по темам квиза: r ≈ 0,47; сторона явных клеток совпадает в 80 %.
